# AGENTS.md

PiS is a desktop shell for [pi](https://pi.dev): a Go app built on [mygo](https://mygo.run) hosts a React UI and runs the user's installed `pi` over JSONL RPC. PiS does not bundle pi, store credentials, or keep a second session or configuration store.

This file is the agent entry point. The engineering record is in [`docs-dev/`](docs-dev/): [architecture](docs-dev/architecture.md), [development](docs-dev/development.md), [testing](docs-dev/testing.md), [UX](docs-dev/ux.md), [design system](docs-dev/design-system.md), and [release](docs-dev/release.md). The user guide is [`docs-user/`](docs-user/). Format: <https://agents.md/>.

## Setup and checks

- Install: `bun install`. Use bun, not npm; do not hand-edit `bun.lock`.
- Full app: `bun run dev` (mygo window and hot reload).
- Web only: `bun run dev:web` (mock data; not a real pi test).
- User docs: `bun run docs:dev`.
- Format: `bun run format`.
- Full gate: `bun run check` (= `scripts/check.sh`: gofmt, Go build/vet/test, Vite+ format/lint/typecheck, bridge tests, Vitest, frontend build, docs build).
- Focused checks: `bun run check:web`, `bun run test`, `bun run test:bridge`, `go test ./internal/... .`.
- The pre-commit hook runs the full gate. Do not bypass a failed format, lint, type, or test check.

## Generated files

- `frontend/src/mygo.ts` is generated from Go exports by `bun run generate`. Never edit it by hand. Regenerate after changing a bound Go method, request, or response type.
- `frontend/src/lib/cn-tables.ts` is generated by `bun run cn:build` from `frontend/src/styles.css`. Run it after changing the Tailwind theme (`@theme`, text, color, radius, shadow, or container tokens). The script also formats the file.
- Build outputs (`build/`, `frontend/dist/`, `docs-user-build/`) are generated; never edit or commit them.

## Architecture and data boundaries

- `main.go` binds services with `mygo.BindAs`; `frontend/src/mygo.ts` mirrors that surface. Every exported Go method is callable by the renderer, so keep the IPC surface small and validate inputs at the boundary.
- `internal/agent` starts one `pi --mode rpc` child per open session. `internal/bridge` is a bundled pi extension for session tree, plan mode, and approvals.
- PiS reads pi session JSONL. It writes pi's `mcp.json`, `settings.json`, and `models.json` only after an explicit user action in the app, atomically and while preserving unknown fields. It never writes pi `trust.json`, `auth.json`, or session content. Do not add credential storage or logging; a custom provider key goes to pi's `models.json` and is never returned to the page or logs.
- pi must be `>= 1.6 < 2`; the app checks this and shows a warning otherwise.
- Project trust gates project-local pi resources. PiS stores its own trust decision and never writes pi's trust file.
- Smart approvals and plan mode are guardrails, not a sandbox; do not describe them as one.

## Frontend

- React 19, Zustand, Base UI, and Tailwind v4. IPC wrappers are in `frontend/src/lib/api.ts`; chat state is in `frontend/src/store/chat.ts`.
- Use the semantic token layer in `frontend/src/styles.css` (`bg-surface`, `text-subtle`, `border-control`, …) and the type scale (`text-micro`, `text-label`, `text-body`, `text-body-lg`, `text-title`, `text-heading`, `text-display`). Do not add arbitrary font sizes, raw hex colors, or `text-[13px]` in components.
- Palettes are applied through `data-palette` and `light-dark()`. Do not add per-palette component branches; add or change the tokens in `styles.css` instead.
- Use the shared primitives in `frontend/src/components/ui/`: Button, DialogSurface/DialogHeader, Field/TextInput, Kbd, SectionLabel, and StatusPill. Import `cn` from `frontend/src/lib/cn.ts`, never from the `cn` package directly.
- All user-facing copy goes through `t()` in `frontend/src/lib/i18n.ts`. Add the Chinese entry in the same change and keep the English source string stable.
- Follow the existing naming: PascalCase for component files, kebab-case for `lib/` and `store/` modules. Tests live next to the code as `*.test.ts` and mock the IPC boundary.
- `bun run dev:web` uses `frontend/src/lib/mock.ts`. Mock data is for layout only; verify pi behavior with a real pi.
- Interaction-heavy UI changes need a check in `bun run dev`; unit tests and the mock page do not cover mygo or real pi.

## Settings

- `internal/settings/settings.go` owns the schema (`Version`) and migration in `merge`.
- Adding a setting: add the field and default, bump `Version` when older files cannot have it, migrate older versions in `merge`, and add a test. Optional preference fields in `internal/app/service.go` are pointers so "unset" stays distinct.
- Keep palette ids in `settings.Palette.Valid()` and `frontend/src/lib/types.ts` (`PALETTES`/`paletteOf`). `frontend/src/mygo.ts` intentionally types them as `string`.

## Documentation

- Code and docs change together. When you change behavior, settings, IPC, release steps, or user-facing copy, update the matching docs in the same change. Do not leave a claim that the code now contradicts.
- `README.md` / `README.zh.md`: public overview and release status.
- `AGENTS.md`: agent entry point; update it when commands, conventions, generated files, or release steps change.
- `docs-dev/*.md` / `*.zh.md`: engineering record (architecture, development, testing, UX, design system, release).
- `docs-user/en/**` and `docs-user/zh/**`: Rspress user guide; images live in `docs-user/public/images/`. Keep both languages in sync.
- `CHANGELOG.md` / `CHANGELOG.zh.md`: release record for user-visible changes.
- Search the existing docs before adding a page. Update or remove stale statements instead of duplicating them.

## Release

- `CHANGELOG.md` and `CHANGELOG.zh.md` are the release record. Add the same version section to both; `scripts/release.sh` refuses to publish without the Chinese section.
- `scripts/release.sh` runs the full check, commits `chore(release): prepare <version>`, pushes `main` and the tag, waits for the Release workflow, verifies the draft, and publishes with generated notes.
- Release notes are `scripts/release-notes-header.md` followed by the CHANGELOG section. Keep the header's asset names, install commands, and first-launch notes in sync with the build.
- Delta updates are off (`updates.deltas: 0`) and the draft check rejects `.delta` assets. Do not add them back without an explicit decision; updates download the full archive.
- Never commit, print, or log update private keys or credentials. Signing and notarization are optional and read from environment variables.
- Published release notes and assets are public history. Do not edit or delete them without an explicit request in the current task.

## Commits and pull requests

- Use [Conventional Commits](https://www.conventionalcommits.org/): `<type>(<scope>): <summary>`, for example `feat(frontend): add the palette picker`.
- Types: `feat`, `fix`, `docs`, `refactor`, `perf`, `test`, `build`, `ci`, and `chore`. Use a scope where it helps (`frontend`, `settings`, `agent`, `bridge`, `release`, `docs`); omit it when the change is repository-wide.
- Summaries are imperative, lowercase, and have no trailing period. Put the reason in the body. Mark breaking changes with `!` and a `BREAKING CHANGE:` footer.
- The release script's automated commit is `chore(release): prepare <version>`.
- Keep each commit focused on one coherent change. Include the generated files that belong to it (`mygo.ts`, `cn-tables.ts`); do not mix unrelated formatting.
- Run `bun run format` and `bun run check` before committing.
- Do not add AI or tool attribution (`Co-Authored-By`, `noreply` addresses) to commits, pull requests, or issues.
